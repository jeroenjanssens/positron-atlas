At a glance

Positron Atlas turns the rows of a DataFrame into a map: every point is a row, and rows that are similar end up close together. Three parts work together. The Python kernel (your Positron session) holds the data and does the heavy work. The webview (the Atlas tab) computes the UMAP layout and draws the map. The extension host (Positron's Node.js process) connects the two.

1 · Prepare (kernel). The selected numeric columns are read as float32, sampled, cleaned and standardized (optionally reduced with PCA). A random subset of rows becomes the anchors. A background thread already finds each row's nearest anchors.
2 · UMAP (webview). UMAP runs in a web worker on the anchors only (up to 100,000), on the GPU when available, and you watch it converge. Alternatives: UMAP in the kernel (polars-umap, umap-learn), or existing coordinate columns (Layout → From columns).
3 · Place all rows (kernel). Every other row is placed at the weighted mean of its 10 nearest anchors' positions. This is what makes 10 million rows fast; re-placing after a live change reuses the cached neighbours.
4 · Draw (webview). deck.gl draws the points (2D or 3D) with colours, sizes, filters, labels, outlines and annotations. Colours, titles and other per-row values are fetched from the kernel as binary files.
5 · Explore (all three). Hover asks the kernel for rows; the lasso, tags and clusters can be written back to the DataFrame after a confirmation; maps export as PNG, HTML or DataMapPlot.

1Overview

Atlas runs in three processes that never share memory: the webview (a Chromium page inside Positron), the extension host (Node.js), and your Python kernel. Small messages travel as JSON; bulk arrays travel as raw binary files in a per-panel job directory, which is why the kernel and Positron must share a file system. Your DataFrame stays in the kernel: only the selected numeric columns are converted to float32, and only the anchors (a sample of rows), the 2D coordinates and the colour codes reach the webview.

1postMessage: typed messages (src/shared/protocol.ts). Arrays going to the host (anchor layout, selection masks, label codes, PNG bytes) are sent as Uint8Arrays, without base64.
2evaluateCode: every kernel call is a silent Python expression returning a JSON string. Long tasks run in a job thread; the host polls status().
3Kernel files: the kernel writes outputs atomically (.tmp then rename) and reads the host's input files.
4fetch(): the webview reads outputs through asWebviewUri URIs straight into typed arrays: no JSON, no base64.
5Host files: the host writes the webview's bytes into files for the kernel and deletes them after the call. It also caches downloaded images (image-URL columns) and fonts.

2Data flow, step by step

From opening a DataFrame to a map with every row placed. Solid arrows are calls or messages, dashed arrows are replies, green arrows are file reads and writes. With fewer rows than the anchor limit, every row is an anchor and the "Place all rows" phase is skipped. The kernel can also run an exact UMAP on all rows (polars-umap or umap-learn) instead of browser UMAP plus placement; its output arrives the same way as placement's xy_*.f32 chunks.

  • Your DataFrame, and any column you did not select as a feature.

5Potential optimizations

Each one was checked against the code. Timings come from docs/benchmarks.md; "expected" numbers are estimates, not measurements. Most of the heavy work is already well optimized (Rust placement at 11–13× numpy, factorized colours, row-major polars reads), so these are about repeated work and the slow paths.

1 · Keep the nearest anchors of each row between placements done · measured 27–110× faster re-placement (docs/benchmarks.md)

Every placement builds the anchor index again and searches the 10 nearest anchors of every row again (_project_impl and _project_native in python/positron_atlas_kernel.py, place_rows in rust/atlas-core/src/place.rs). But those neighbours depend only on the prepared features, the anchors and the metric, not on the UMAP layout. A live min_dist change, an n_neighbors rebuild or a new UMAP seed all re-place every row for nothing.

Store the neighbour indices (u32) and distances (f32) after the first placement and keep them until the next prepare or a metric change (neighbors() already exists in the Rust core; numpy has AnchorIndex.query + place_from_neighbors). A re-placement then becomes a weighted mean: expected ≈ 0.05–0.1 s instead of 1.4–1.9 s (Rust) or 16 s (numpy) for 10⁶ rows. Memory: 80 B per row (80 MB per 10⁶ rows), so keep a cap (e.g. 1 GiB) or store distances as f16. Note that the index's k-means uses the UMAP seed today; give it its own fixed seed so a new UMAP seed keeps the cache.

Evidence: e2e benchmark "Live min_dist change, then automatic re-placement: 4.0 s" (300,000 rows), most of it the repeated search.

2 · Search the neighbours while the browser runs UMAP done · own thread after prepare

After prepare, the kernel is idle while the webview computes the anchor layout (1–10 s on WebGPU, much longer on the CPU). The neighbour search does not need the layout, so start it as a job right after prepare. When UMAP finishes, placement is only the weighted mean, and "Place all rows" could happen automatically for much larger frames than today's 20 s estimate threshold allows. With the CPU UMAP (WASM, one thread) the two do not compete for cores; the Rust search uses rayon, so cap its threads when the browser runs on the CPU, or accept some slowdown.

Evidence: the job thread starts project only after the webview posts its layout (project() in atlas.svelte.ts). A job runs one task at a time (_Job.run), so this needs a second slot or a "neighbours" stage inside prepare.

3 · Without WebGPU, compute the anchor layout in the kernel impact: high on CPU-only machines · effort: low

The browser's CPU fallback runs WASM on one thread: 74 s for 100,000 anchors, which is why maxAnchorsCpu defaults to 25,000. polars-umap in the kernel uses every core: 12.4 s for 100,000 × 50 rows on a 4-core machine. When navigator.gpu is missing and polars-umap is installed, suggest (or default to) the kernel engine, and allow the larger anchor count with it. The cost is the live animation and the live parameter changes.

Evidence: docs/benchmarks.md (browser UMAP table; exact UMAP table).

4 · Send arrays to the host as binary, not base64 done · raw Uint8Arrays (300× less encoding time for a 10⁶-row mask)

Label codes and cluster codes go to the host as base64 of one u16 per prepared row (writeLabels, describeGroups), and masks as packed bits. At 10⁷ rows that is a 27 MB string built in 32 KB slices (bytesToBase64 in src/webview/vscode.ts), copied through IPC and decoded again. Recent VS Code versions transfer ArrayBuffers in webview messages without JSON encoding; check that Positron's webview supports it, then post Uint8Arrays. The anchor layout for each placement (≈ 1 MB) benefits too.

5 · Shorter waits on job status done · 150 ms cap, chunks from 10⁵ rows

The host polls status() with a backoff up to 500 ms, and each poll is a kernel execution. Short tasks (prepare on small frames, the last chunk of a placement) can wait up to half a second after they finish, and placement chunks are 10⁶ rows, so on large frames the first points appear late. Cap the backoff lower (≈ 150 ms) while a task runs, and make the first placement chunk small (e.g. 10⁵ rows) so the map fills in sooner.

Evidence: waitForJob in src/extension/kernelBridge.ts; chunkRows default in _project_impl.

6 · Small copies first item done (anchors reused)

  • _project_impl gathers x[job.anchor_pos] again on every call although the anchors were already gathered in prepare (20 MB in the example). Moot with #1.
  • The webview keeps its own copy of the anchors after sending one to the worker (this.anchors.slice() in startUmap), 20 MB in the example. It is needed to restart UMAP; it could be fetched again from anchors.f32 instead.

Considered and not worth it: a faster hover index (it is a single O(n) grid pass, built on first hover), Rust for PCA (BLAS already does the work; see docs/benchmarks.md), and other approximate nearest-neighbour indexes (the IVF index is 8–40× faster than nndescent or HNSW at similar recall).
